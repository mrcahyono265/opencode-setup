# UI Review

## Use

Use for pages, dashboards, forms, landing pages, admin UI, responsive layouts, UX, and component consistency. Do not use for backend-only work.

## Review

Assess the user goal, hierarchy, navigation, layout, typography, components, forms, tables, states, mobile behavior, accessibility, visual consistency, and UI copy.

- Avoid clutter, excessive empty space, duplicate component styles, overcrowded tables, blank important pages, layout shifts, vague actions, and technical error jargon.
- Forms need labels, visible required fields, validation, helpful errors, loading, and success feedback.
- Empty states explain why and the next action; errors explain recovery.
- Design mobile-first when practical. Accessibility requires semantic HTML, keyboard operation, contrast, focus states, and screen-reader support.
- Define visual direction before implementation. Use inspiration to understand a quality, never copy a layout.

Read `references/review-checklist.md` only for a deep audit or a high-stakes UI decision.

## Report

Give practical recommendations: what works, what to improve, why it matters, and its UX, accessibility, maintainability, or consistency impact. Do not claim only that something “looks better.”

Use: Summary, Strengths, Weaknesses, Opportunities, UX, Accessibility, Responsive Review, Recommended Changes. Do not generate implementation code unless requested.
